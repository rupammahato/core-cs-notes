## Why this module matters

A database query can be correct and still be too expensive to repeat on every request. A useful operation can take longer than an HTTP response budget. An uploaded file can parse successfully while producing duplicate, stale or cross-tenant records. Caches, background jobs and ingestion solve different parts of that picture.

Interview follow-ups often connect them: Why did a cache return stale data after invalidation? What if a worker runs twice? What happens when the worker dies after a write? How does an import resume after committing only some rows? Why did a spreadsheet formula become a security issue during export?

> **Keep authoritative state explicit, make repeated work safe, and commit progress with the state it describes.**

This module follows a cached catalog read, a durable local job and a restartable import. It includes a Redis bridge and the GCP Cloud Tasks delivery model relevant to the resume, while clearly separating those documented services from the code actually executed.

## 15.1 Separate cache, queue, schedule and import

| Tool / concept | Main problem | What it does not supply automatically |
| --- | --- | --- |
| Cache | Reuse a derived/read result cheaply | Authoritative correctness, freshness or authorization |
| Queue | Retain/deliver work outside the immediate request | Exactly-once business effects or infinite worker capacity |
| Scheduler / cron | Decide when work should be triggered | Durable completion, duplicate protection or overlap control |
| In-process background task | Continue work in the current application process | Survival of process loss or coordinated retries across replicas |
| Ingestion pipeline | Convert external bytes into trusted internal records | Correct identity, ordering, reconciliation or restart policy |

A cache miss should normally fall back to authoritative data. A queue backlog should normally preserve accepted work while delaying completion. An import failure needs a visible progress/error outcome, not a cache-like “try another lookup” policy.

```text
request -> authorized read -> cache -> miss -> authoritative database
request -> durable job acceptance -> worker -> durable outcome
schedule -> enqueue a run -> same worker/retry/idempotency protocol
upload -> immutable source -> parse/validate -> batches -> records + checkpoints
```

Use an in-process task for deliberately best-effort or tightly bounded work whose loss is acceptable. If the response promises a durable operation, persist its acceptance before reporting success. A 202 Accepted response should identify a durable job/status resource; it is not proof that the work completed.

Cron can trigger an import every night, but the import still needs overlap protection, source identity, checkpoints and failure alerts. Multiple replicas running the same schedule can create duplicates unless one scheduler or durable business identity coordinates them.

## 15.2 Cache-aside and the freshness contract

Cache-aside means the application checks a cache, reads the primary on a miss and stores the result for reuse. On a successful primary write, it invalidates or refreshes the relevant cached representation.

```text
READ:  authorize -> build scoped key -> cache hit -> return
                                    -> miss -> primary read -> fill -> return
WRITE: authorize -> primary transaction commits -> invalidate affected keys
```

Choose what stale data the product can tolerate. A public catalog description might tolerate a short delay. Stock reservation, account balance, permission revocation and payment state need an authoritative decision at the write/security boundary even if a cached display exists.

### Key identity must include the answer's context

A useful key contains tenant/resource identity and representation version. If an answer varies by permissions, locale, filters or projection, the key or cache placement must account for that variation. Authorize before serving cached protected data. A tenant-only key does not safely cache two different users' permission-filtered results.

The example uses a tuple to avoid ambiguous string concatenation. In a remote cache, define a stable encoding and namespace. Do not store raw credentials in keys or emit private cached values into unrestricted logs.

### TTL, eviction and invalidation

TTL makes an entry unusable after its expiry policy; it is not the same as memory-pressure eviction. Capacity controls how much data remains; an LRU policy removes a least-recently-used entry under pressure. Either can cause a miss.

Negative caching stores an absent result for a short time. It reduces repeated nonexistent lookups but can delay visibility of newly created objects. Scope negative entries too, and distinguish an authoritative not-found from a transient database failure. The code caches None with a shorter TTL and does not cache loader exceptions.

A TTL starts at the chosen fill boundary. It does not prove a universal bound from the original database write: a delayed reader can fetch an older version and fill later. Long-running requests, asynchronous replicas and repeated stale fills complicate freshness. State the actual consistency contract rather than saying “TTL guarantees latest data.”

## 15.3 Verified local cache: collapse work and fence late fills

### Exact implementation: cache.py

```python
from collections import OrderedDict
from concurrent.futures import Future
from copy import deepcopy
from threading import RLock,Condition
from time import monotonic

class TTLCache:
    """Bounded, process-local cache; never a Redis implementation."""
    def __init__(self,*,capacity=32,ttl=10,negative_ttl=2,clock=monotonic):
        if type(capacity) is not int or capacity<1 or ttl<=0 or negative_ttl<=0:
            raise ValueError('invalid cache configuration')
        self.capacity,self.ttl,self.negative_ttl,self.clock=capacity,ttl,negative_ttl,clock
        self.entries=OrderedDict();self.flights={};self.epoch=0
        self.lock=RLock();self.changed=Condition(self.lock)
        self.stats={'hits':0,'loads':0,'waits':0}

    def invalidate(self,key):
        with self.lock:
            self.entries.pop(key,None)
            self.epoch+=1  # Conservative: any invalidation fences all current fills.

    def get_or_load(self,key,loader,*,wait_seconds=5):
        with self.lock:
            entry=self.entries.get(key)
            if entry is not None and self.clock()<entry[0]:
                self.entries.move_to_end(key);self.stats['hits']+=1
                return deepcopy(entry[1])
            self.entries.pop(key,None)
            future=self.flights.get(key)
            if future is None:
                future=Future();self.flights[key]=future;leader=True;epoch=self.epoch
                self.stats['loads']+=1
            else:
                leader=False;self.stats['waits']+=1;self.changed.notify_all()
        if not leader:
            return deepcopy(future.result(timeout=wait_seconds))
        try:
            value=loader()
            saved=deepcopy(value)
            with self.lock:
                if self.epoch==epoch:
                    duration=self.negative_ttl if value is None else self.ttl
                    self.entries[key]=(self.clock()+duration,saved)
                    while len(self.entries)>self.capacity:self.entries.popitem(last=False)
            future.set_result(saved)
            return deepcopy(saved)
        except BaseException as error:
            future.set_exception(error)
            raise
        finally:
            with self.lock:self.flights.pop(key,None)

def cache_key(tenant_id,resource_id,representation='summary-v1'):
    if type(tenant_id) is not int or tenant_id<1 or type(resource_id) is not str:
        raise ValueError('invalid cache scope')
    return ('catalog',tenant_id,resource_id,representation)
```

### Cache stampede

When many callers miss the same popular key, independent loads can multiply primary work. This implementation keeps one in-flight Future per key: the leader loads outside the global lock; followers wait for its result. Other keys can still load independently.

The verifier coordinates eight real callers and observes seven waiting followers before releasing the leader. All receive the result from one loader invocation. This is process-local coordination: separate web processes have separate caches/flights and could each load the same key.

Entry capacity is bounded; simultaneous unique-key flights still need an application concurrency limit. Followers have a wait timeout, but the loader's own I/O needs its own deadline/cancellation policy. The cache is not a scheduler or a hard resource sandbox.

### The late-fill invalidation race

Without a guard:

```text
reader loads old primary version
writer commits new version and deletes cache key
old reader fills cache after deletion
next request receives the old value again
```

The implementation captures an epoch when a load starts. Invalidation increments it, so that older load cannot store its value after invalidation. The epoch is global and conservative: invalidating one key can prevent unrelated in-flight fills, causing extra misses rather than unsafe reuse.

An already-running request can still return its older result, and a caller joining that existing flight can receive it too. The guarantee here is narrower: the old fill does not repopulate the cache. This is not linearizable reads or a cross-process fencing protocol.

The fixture pauses an old load, changes the source and invalidates, then releases it. The in-flight response is 1; the next fresh read is 2. It also verifies copies prevent callers or loader-owned objects from mutating saved entries.

### Other freshness patterns

Write-through updates a cache as part of the application's write path, but a separate database/cache still has a dual-write failure problem. Write-behind delays persistence and requires a much stronger loss/recovery policy. Stale-while-revalidate serves older data while refreshing, trading freshness for availability/latency; it requires explicit stale limits and refresh ownership.

Versioned keys or monotonic entity versions can prevent old values replacing new representations when the participating components enforce the protocol. An outbox/change stream can propagate invalidations after commit, but delivery lag/duplicates remain. None of those distributed mechanisms is implemented by this local epoch.

## 15.4 Redis bridge: shared cache is still a protocol

Redis is a networked data store with string and richer data structures, used here as a supporting cache concept. It can share cached data across application processes, while introducing connection, serialization, timeout, memory and availability decisions.

A documented cache-aside path uses GET, SET with expiration and DEL after the primary write. SET can combine value and expiration options in one command. These are documented commands, not recorded executions in this module. References: [Redis cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/), [SET options](https://redis.io/docs/latest/commands/set/).

TTL and Redis maxmemory eviction policies solve different problems. Choose an eviction policy suitable for disposable cached data, and do not accidentally treat evictable cache entries as the only durable job/authorization record. Reference: [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/).

A Redis NX/expiry lock needs an ownership token and an atomic ownership-checked release. A paused owner can outlive its lease; blindly deleting the key can release a successor's lock. A cache-fill lock may reduce stampedes, but a business correctness rule may need fencing enforced by the protected resource itself. Reference: [Redis lock ownership and lease considerations](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).

If Redis fails, choose bounded fallback behavior. Unbounded simultaneous database fallbacks can turn a cache outage into a database outage. Use primary capacity limits, time budgets and measured degradation policy. Cache hit ratio alone is insufficient: inspect primary load, stale responses, loader waits, timeouts and invalidation lag. This chapter reports functional checks, not Redis latency or a benchmark.

## 15.5 Durable jobs: identity, attempts, leases and outcomes

A job needs more than a payload. Define its trusted tenant, business operation key, payload/version, due time, state, attempt count, current ownership and terminal outcome. A delivery ID is not always the business identity: a producer may submit the same operation again under another delivery ID.

```text
ready -- due claim --> running -- successful local commit --> done
                         |
                         +-- transient failure --> ready at a later time
                         +-- permanent/exhausted --> failed
                         +-- lease expires --> eligible for a new owner/attempt
```

A lease gives temporary ownership, not certainty that the former worker stopped. A token lets the store reject a stale worker's completion after another worker has reclaimed the job. Heartbeats/renewals need the same ownership condition and a policy for maximum execution; renewal is not implemented here.

### Exact local store and transaction boundary: store.py

```python
from contextlib import contextmanager
from pathlib import Path
import sqlite3

SCHEMA='''
CREATE TABLE jobs(
 id TEXT PRIMARY KEY,tenant_id INTEGER NOT NULL CHECK(tenant_id>0),
 operation_key TEXT NOT NULL,payload TEXT NOT NULL,
 state TEXT NOT NULL CHECK(state IN ('ready','running','done','failed')),
 attempts INTEGER NOT NULL DEFAULT 0,available_at REAL NOT NULL,
 lease_until REAL,token TEXT,last_error TEXT,
 UNIQUE(tenant_id,operation_key));
CREATE TABLE effects(tenant_id INTEGER NOT NULL,operation_key TEXT NOT NULL,
 amount INTEGER NOT NULL CHECK(amount>0),PRIMARY KEY(tenant_id,operation_key));
CREATE TABLE imports(tenant_id INTEGER NOT NULL,import_key TEXT NOT NULL,digest TEXT NOT NULL,
 checkpoint INTEGER NOT NULL DEFAULT 0,state TEXT NOT NULL DEFAULT 'running',
 PRIMARY KEY(tenant_id,import_key));
CREATE TABLE records(tenant_id INTEGER NOT NULL,external_id TEXT NOT NULL,
 name TEXT NOT NULL,amount_minor INTEGER NOT NULL CHECK(amount_minor>=0),
 source_version INTEGER NOT NULL CHECK(source_version>=0),source_time TEXT NOT NULL,
 PRIMARY KEY(tenant_id,external_id));
'''

@contextmanager
def connect(filename):
    conn=sqlite3.connect(filename,isolation_level=None,timeout=3)
    conn.row_factory=sqlite3.Row
    try:yield conn
    finally:conn.close()

def prepare(filename):
    with connect(filename) as conn:conn.executescript(SCHEMA)

@contextmanager
def transaction(conn):
    if conn.in_transaction:raise ValueError('transaction owner requires idle connection')
    conn.execute('BEGIN IMMEDIATE')
    try:
        yield
        conn.execute('COMMIT')
    except BaseException:
        conn.execute('ROLLBACK')
        raise
```

This is a SQLite teaching store with one-writer coordination through BEGIN IMMEDIATE. It provides real durable rows and transactions for the local protocol. It is not a scalable general-purpose broker implementation. M13 shows the different PostgreSQL row-lock/SKIP LOCKED mechanisms on that actual engine.

The connection context closes explicitly; a plain sqlite3 connection's own context manager is not a general promise to close the connection. The transaction helper requires an idle connection and owns commit/rollback. Values use placeholders. References: [Python sqlite3 transactions/connections](https://docs.python.org/3.12/library/sqlite3.html), [M13 database coordination](/docs/resume-skills/postgresql-backend).

### Exact job implementation: jobs.py

```python
import json
from uuid import uuid4
from store import transaction

def backoff(attempt,*,base=2,cap=8):
    if type(attempt) is not int or attempt<1:raise ValueError('invalid attempt')
    return min(cap,base*2**min(attempt-1,20))

def enqueue(conn,*,tenant_id,operation_key,amount,now):
    if type(tenant_id) is not int or tenant_id<1 or type(amount) is not int or not 1<=amount<=1000:
        raise ValueError('invalid payload')
    if type(operation_key) is not str or not 1<=len(operation_key)<=80:raise ValueError('invalid key')
    payload=json.dumps({'amount':amount},sort_keys=True)
    with transaction(conn):
        conn.execute('INSERT INTO jobs(id,tenant_id,operation_key,payload,state,available_at) VALUES(?,?,?,?,?,?) ON CONFLICT(tenant_id,operation_key) DO NOTHING',
                     (str(uuid4()),tenant_id,operation_key,payload,'ready',now))
        row=conn.execute('SELECT * FROM jobs WHERE tenant_id=? AND operation_key=?',(tenant_id,operation_key)).fetchone()
        if row['payload']!=payload:raise ValueError('idempotency payload conflict')
        return row['id']

def claim(conn,*,now,lease_seconds=10,max_attempts=3):
    if lease_seconds<=0 or type(max_attempts) is not int or max_attempts<1:raise ValueError('invalid lease policy')
    with transaction(conn):
        conn.execute("UPDATE jobs SET state='failed',token=NULL,lease_until=NULL,last_error='attempts_exhausted' WHERE state='running' AND lease_until<=? AND attempts>=?",(now,max_attempts))
        row=conn.execute("SELECT * FROM jobs WHERE attempts<? AND ((state='ready' AND available_at<=?) OR (state='running' AND lease_until<=?)) ORDER BY available_at,id LIMIT 1",(max_attempts,now,now)).fetchone()
        if row is None:return None
        token=str(uuid4())
        conn.execute("UPDATE jobs SET state='running',attempts=attempts+1,token=?,lease_until=? WHERE id=?",(token,now+lease_seconds,row['id']))
        return dict(conn.execute('SELECT * FROM jobs WHERE id=?',(row['id'],)).fetchone())

def finish(conn,owned,*,now,fail_before_commit=False):
    with transaction(conn):
        row=conn.execute("SELECT * FROM jobs WHERE id=? AND tenant_id=? AND token=? AND state='running' AND lease_until>?",
                         (owned['id'],owned['tenant_id'],owned['token'],now)).fetchone()
        if row is None:return False
        amount=json.loads(row['payload'])['amount']
        conn.execute('INSERT INTO effects VALUES(?,?,?) ON CONFLICT(tenant_id,operation_key) DO NOTHING',
                     (row['tenant_id'],row['operation_key'],amount))
        if fail_before_commit:raise RuntimeError('injected before local effect/job commit')
        conn.execute("UPDATE jobs SET state='done',token=NULL,lease_until=NULL,last_error=NULL WHERE id=?",(row['id'],))
        return True

def fail(conn,owned,*,now,retryable=True,max_attempts=3):
    with transaction(conn):
        row=conn.execute("SELECT * FROM jobs WHERE id=? AND token=? AND state='running' AND lease_until>?",(owned['id'],owned['token'],now)).fetchone()
        if row is None:return False
        terminal=not retryable or row['attempts']>=max_attempts
        conn.execute('UPDATE jobs SET state=?,available_at=?,lease_until=NULL,token=NULL,last_error=? WHERE id=?',
                     ('failed' if terminal else 'ready',now+backoff(row['attempts']),'permanent' if not retryable else 'transient',row['id']))
        return True
```

The payload is deliberately small: one positive integer amount. This is an illustrative local business effect, not a real account credit, payment or external API. Enqueue accepts a trusted tenant and unique operation key; a repeated key returns the same job, while changed payload is a conflict.

claim() serializes selection and ownership update. It skips work not yet due, increments attempts and creates a fresh token/lease. Expired abandoned claims can be reclaimed, but a configured attempt limit eventually moves exhausted work to failed. The test clock supplies now explicitly; production workers need a consistent time authority and a lease policy resilient to pauses/skew.

finish() verifies current token, tenant, state and unexpired lease. It inserts a unique local effect and marks the job done in one transaction. A repeated/stale completion cannot apply another local effect. fail() checks ownership before rescheduling or making the failure terminal. All callers must use the same intended policy; differing per-call attempt limits are not a coordination feature.

### Actual ownership and retry evidence

Two real threads with separate SQLite connections compete for one ready job; one receives ownership. When a lease expires, the replacement gets a different token and attempt 2. Both completion and failure reports from the former owner are rejected.

The local retry sequence is **2,4,8,8** time units, capped at 8. This deterministic helper omits jitter so its boundaries are easy to verify. Production policy should consider bounded jitter, deadline/age, retry budgets, provider Retry-After and overload; do not label this sequence Cloud Tasks' exact algorithm.

### Local exactly-once effect versus external delivery

The unique effect record and done state share one local transaction. If failure is injected between them, both roll back; after lease expiry, a new attempt succeeds once. Reopening a connection sees the committed state. Those are database/application checks, not machine-crash or power-loss recovery tests.

A token check at the database does not cancel an old worker's already-running provider call. For an external effect:

```text
provider accepts operation
worker loses response / stops before marking local completion
replacement retries
provider may receive the same operation again
```

Use a stable provider idempotency key when supported, durable operation/result state and reconciliation of ambiguous outcomes. If the provider has no deduplication/lookup protocol, universal exactly-once effects cannot be obtained merely by writing a local done row.

### Failed work is a product state

Distinguish transient failure, invalid permanent input, exhausted retries, superseded source version and operator cancellation. Preserve enough sanitized context to diagnose and replay the intended operation. A failed/dead-letter store needs retention, visibility and an explicit replay policy; replaying every failure can reintroduce old data or duplicate an external effect.

Retry the smallest complete safe operation. Avoid a web retry, queue retry, SDK retry and database retry multiplying without one budget. More concurrency can worsen an overloaded dependency; a queue buffers pressure but does not create capacity.

## 15.6 GCP Cloud Tasks: map the resume skill to the mechanism

Cloud Tasks is a managed task-delivery service. A producer creates an HTTP-target task in a queue; Cloud Tasks dispatches an HTTP request to a handler. Queue configuration controls delivery rates, concurrency and retries. The handler owns the actual business operation and its durable outcome.

```text
producer -> CreateTask -> queue retains scheduled work
                         -> authenticated HTTP dispatch -> worker handler
                         -> success response: task complete
                         -> failure/no successful response: retry policy applies
```

No GCP project, credential, queue or HTTP target is used by these examples. The local SQLite failed state, leasing algorithm and retry function are design lessons, not an exact implementation of managed service internals.

### Delivery is not a business exactly-once guarantee

Cloud Tasks can execute duplicates and does not guarantee FIFO execution. A later task may run before an earlier one. Workers therefore need safe replay and source-version/state guards where ordering matters. Task-name deduplication constrains task creation within the service's retention rules; it is not a lifetime business ledger. References: [execution/duplicate limitations](https://docs.cloud.google.com/tasks/docs/common-pitfalls), [task creation/deduplication](https://docs.cloud.google.com/tasks/docs/create-tasks).

A successful HTTP response acknowledges task handling. Return success after the required durable work or a deliberately recorded terminal outcome, not immediately after starting an untracked in-process coroutine. If a payload has a permanent business defect, decide how to persist that failure and stop repeating it. Do not assume a 4xx response automatically means the managed queue will permanently discard it.

### Authenticate the dispatch

Use the appropriate service identity and authenticated target configuration. For an OIDC-protected handler, validate the token's signature, issuer, audience and time claims through the selected platform/verifier, and authorize the expected identity. Informational X-CloudTasks headers are not authentication; a public caller can imitate a header.

After authenticating the dispatcher, still resolve the job's trusted tenant and operation from durable state. A valid service token does not make an arbitrary client-supplied tenant/file URI safe. Never let task payloads choose unrestricted URLs or filesystem paths. Reference: [HTTP target creation and authentication](https://docs.cloud.google.com/tasks/docs/creating-http-target-tasks).

### Rate, concurrency and retry are different controls

Rate bounds dispatches over time; concurrency bounds simultaneous in-flight handlers. Slow work can saturate concurrency even with a modest dispatch rate. Cloud Tasks can also apply system throttling and ramp-up behavior, so configuration is not a promise of exact observed throughput.

Cloud Tasks uses its documented retry/backoff parameters and attempt/duration semantics. Do not copy the local attempts-only stopping rule or capped exponential function and call it an emulator. Read the selected RetryConfig: combined limits do not necessarily mean “stop immediately when either number is reached.” Reference: [queue routing, limits and retries](https://docs.cloud.google.com/tasks/docs/configuring-queues).

For an embedding worker, keep document/version/model identity in the operation key, avoid repeating expensive API calls blindly and record result/reconciliation state. M23 develops that pipeline; no model API or paid embedding call is made here.

### The producer's dual-write gap

Committing business state and then calling CreateTask can leave a committed operation without a task if the producer stops between them. Enqueueing first can send work whose business transaction later rolls back. A transactional outbox stores the intent with the business state; a dispatcher retries task creation using a stable identity.

M13/M14 verify atomic outbox **insertion**, not managed delivery. This module verifies a local job/effect transaction, not a Cloud Tasks dispatcher. Keep those claims distinct when discussing a resume project.

## 15.7 Ingestion begins before parsing

An ingestion pipeline turns untrusted external representations into a defined internal model. File extension or Content-Type is a hint, not proof. Accept a deliberate format set and enforce size, structure, identity, value, authorization and resource policies.

```text
authorize tenant/upload
 -> stage immutable bytes under server-owned identity
 -> identify allowed format + byte/archive/page/row budgets
 -> parse into source fields
 -> normalize + validate
 -> write bounded transactions
 -> commit progress with each batch
 -> report complete/partial/failed with sanitized diagnostics
```

Keep original bytes/digest, parser/schema version, source identity and progress where the application needs reproducibility. Store a source event time separately from an ingestion/observation time when both matter. Do not silently replace an invalid timestamp with now.

### The normalized record

This fixture uses external_id, name, amount_minor, source_version and source_time. Tenant is trusted application context, not a field accepted from the file. IDs and versions define identity/order; UTC source time is retained as provenance. Monetary values use integer minor units rather than binary float.

The model deliberately rejects duplicate IDs inside one file instead of letting the last duplicate win. Another system may allow multiple versions in one file, but then it must define ordering and conflict behavior. Error policy is also explicit: validate the entire bounded input before mutating the import store.

### Format-specific risks and contracts

| Format | Useful handling | Trap to explain |
| --- | --- | --- |
| CSV | Explicit encoding/header/dialect, real CSV parser, field/row limits | split(',') breaks quotes; text can become a formula during export |
| Excel/XLSX | Read-only workbook, declared sheets/columns, type/formula policy, archive budgets | data_only may expose cached formula results; ZIP expansion and misleading dimensions |
| XML | Explicit record shape, hardened parser, DTD/entity policy and resource limits | External/entity expansion and unexpectedly deep/large trees |
| PDF | Separate text extraction from structured interpretation; page/resource/OCR policy | Text order is not a reliable table; scanned pages may have no text layer |

Reading a file successfully is not business validation. An amount can parse as a string and still have invalid precision or units. A valid timestamp can be naive and ambiguous. An extracted PDF invoice can still require review before becoming accounting records.

class InvalidFile(ValueError):pass

@dataclass(frozen=True)
class Record:
    external_id:str
    name:str

def bounded(data):
    if not isinstance(data,bytes) or len(data)>MAX_BYTES:raise InvalidFile('file byte limit')
    return data

def normalize(rows):
    records=[];seen=set()
    for number,row in enumerate(rows,1):
        if number>MAX_ROWS:raise InvalidFile('row limit')
        if len(row)!=len(FIELDS):raise InvalidFile(f'record {number}: column count')
        values=[str(v).strip() if v is not None else '' for v in row]
        identifier,name,amount,version,stamp=values
        if not re.fullmatch(r'[A-Za-z0-9_-]{1,64}',identifier) or not 1<=len(name)<=80:
            raise InvalidFile(f'record {number}: identity/name')
        if identifier in seen:raise InvalidFile(f'record {number}: duplicate source identity')
        if not re.fullmatch(r'\d{1,12}',amount) or not re.fullmatch(r'\d{1,9}',version):
            raise InvalidFile(f'record {number}: integer amount/version')
        try:
            parsed=datetime.fromisoformat(stamp)
            if parsed.tzinfo is None:raise ValueError('timezone required')
        except ValueError as error:raise InvalidFile(f'record {number}: aware timestamp required') from error
        records.append(Record(identifier,name,int(amount),int(version),parsed.astimezone(timezone.utc).isoformat()))
        seen.add(identifier)
    if not records:raise InvalidFile('empty data')
    return records

def parse_csv(data):
    try:
        reader=csv.reader(StringIO(bounded(data).decode('utf-8-sig'),newline=''),strict=True)
        if next(reader,None)!=FIELDS:raise InvalidFile('exact CSV header required')
        return normalize(reader)
    except (UnicodeError,csv.Error) as error:raise InvalidFile('CSV encoding/structure') from error

def parse_xml(data):
    root=fromstring(bounded(data),forbid_dtd=True,forbid_entities=True,forbid_external=True)
    if root.tag!='records':raise InvalidFile('XML root')
    rows=[]
    for element in root:
        if element.tag!='record' or [child.tag for child in element]!=FIELDS:raise InvalidFile('XML record shape')
        rows.append([child.text for child in element])
    return normalize(rows)

def parse_xlsx(data):
    stream=BytesIO(bounded(data))
    with zipfile.ZipFile(stream) as archive:
        info=archive.infolist()
        if len(info)>200 or sum(x.file_size for x in info)>8_000_000:raise InvalidFile('XLSX archive budget')
        if any('vbaproject' in x.filename.lower() for x in info):raise InvalidFile('macro content rejected')
    stream.seek(0)
    workbook=load_workbook(stream,read_only=True,data_only=False,keep_links=False)
    try:
        if workbook.sheetnames!=['Records']:raise InvalidFile('one Records worksheet required')
        sheet=workbook['Records'];sheet.reset_dimensions()
        rows=sheet.iter_rows();header=next(rows,())
        if [cell.value for cell in header]!=FIELDS:raise InvalidFile('XLSX header')
        def values():
            for row in rows:
                if any(cell.data_type=='f' for cell in row):raise InvalidFile('formula cells rejected')
                yield [cell.value for cell in row]
        return normalize(values())
    finally:workbook.close()

def extract_pdf(data,*,max_pages=5):
    reader=PdfReader(BytesIO(bounded(data)),strict=True)
    if reader.is_encrypted:raise InvalidFile('encrypted PDF unsupported')
    if len(reader.pages)>max_pages:raise InvalidFile('PDF page limit')
    text='\n'.join(page.extract_text() or '' for page in reader.pages)
    if not text.strip():raise InvalidFile('no extractable text; OCR/review required')
    if len(text)>100_000:raise InvalidFile('PDF extracted-text budget')
    return text.strip()  # Evidence text, not structured financial records.

def import_csv(conn,*,tenant_id,import_key,data,batch_size=2,fail_batch=None,after_commit=None):
    if type(tenant_id) is not int or tenant_id<1 or type(import_key) is not str or not 1<=len(import_key)<=80:
        raise ValueError('invalid trusted import scope')
    if type(batch_size) is not int or not 1<=batch_size<=100:raise ValueError('invalid batch size')
    records=parse_csv(data);digest=sha256(data).hexdigest()
    with transaction(conn):
        conn.execute('INSERT INTO imports(tenant_id,import_key,digest) VALUES(?,?,?) ON CONFLICT(tenant_id,import_key) DO NOTHING',(tenant_id,import_key,digest))
        job=conn.execute('SELECT * FROM imports WHERE tenant_id=? AND import_key=?',(tenant_id,import_key)).fetchone()
        if job['digest']!=digest:raise ValueError('import key reused with changed bytes')
    while True:
        with transaction(conn):
            job=conn.execute('SELECT * FROM imports WHERE tenant_id=? AND import_key=?',(tenant_id,import_key)).fetchone()
            start=job['checkpoint']
            if start==len(records):return start
            end=min(start+batch_size,len(records))
            for row in records[start:end]:
                previous=conn.execute('SELECT * FROM records WHERE tenant_id=? AND external_id=?',(tenant_id,row.external_id)).fetchone()
                if previous and previous['source_version']==row.source_version:
                    if (previous['name'],previous['amount_minor'],previous['source_time'])!=(row.name,row.amount_minor,row.source_time):
                        raise ValueError('same source version has conflicting content')
                conn.execute('''INSERT INTO records VALUES(?,?,?,?,?,?) ON CONFLICT(tenant_id,external_id) DO UPDATE SET
                    name=excluded.name,amount_minor=excluded.amount_minor,source_version=excluded.source_version,source_time=excluded.source_time
                    WHERE excluded.source_version>records.source_version''',
                    (tenant_id,row.external_id,row.name,row.amount_minor,row.source_version,row.source_time))
            if fail_batch==start:raise RuntimeError('injected before batch/checkpoint commit')
            conn.execute('UPDATE imports SET checkpoint=?,state=? WHERE tenant_id=? AND import_key=?',
                         (end,'complete' if end==len(records) else 'running',tenant_id,import_key))
        if after_commit:after_commit(end)

### CSV

The code accepts UTF-8 with optional BOM, exact headers, quoted fields and a bounded row/field budget. A real quoted comma remains part of the name. It rejects malformed encoding/header/column count, fractional or negative minor units, missing timezone, duplicate source identity and over-budget input.

Python's csv parser handles quoting/newlines; it does not infer the business types for this contract. The source timestamp 2026-10-14T12:00:00+05:30 normalizes to **2026-10-14T06:30:00+00:00** in the actual check. Reference: [Python 3.12 CSV](https://docs.python.org/3.12/library/csv.html).

### Excel

XLSX is a ZIP-based container. The fixture checks entry count, total declared uncompressed bytes and macro project content before loading it. It requires exactly one Records worksheet and exact headers. Read-only iteration reduces workbook memory use, and the workbook closes explicitly.

data_only=False lets the code detect and reject formula cells rather than trust cached values. It resets worksheet dimensions so misleading metadata is not accepted as the data boundary. The common normalizer enforces row/value limits. Those are teaching budgets, not complete protection against every hostile compressed/parser workload. Reference: [openpyxl optimized modes](https://openpyxl.readthedocs.io/en/stable/optimized.html).

### XML

defusedxml rejects DTD/entity/external constructs according to the explicit options. The fixture verifies a valid record maps into the same model and an entity-bearing input is rejected. It requires the expected root and ordered child fields.

The bounded input is parsed as a tree; this is not a streaming XML implementation. Large real sources need bounded streaming, nesting/time/memory policy and worker isolation appropriate to the format. References: [Python XML security context](https://docs.python.org/3.12/library/xml.html), [defusedxml project](https://github.com/tiran/defusedxml).

### PDF

pypdf extracts “fixture invoice” from the actual generated text PDF. The code rejects encrypted input, a six-page fixture exceeding the configured page budget, and a blank document without extractable text. The blank check is not evidence that an OCR engine was run.

PDF text is evidence text here, not structured source records passed to the importer. Layout, columns, reading order and scanned images require a separate extraction/review contract. Extraction can allocate/decompress work before a post-extraction text limit is checked; real hostile inputs need process-level time/memory controls. Reference: [pypdf text extraction and limitations](https://pypdf.readthedocs.io/en/stable/user/extract-text.html).

## 15.9 Restartable imports: state and checkpoint in one commit

The importer binds (tenant_id, import_key) to a SHA-256 digest of immutable source bytes. Reusing that key with changed bytes is a conflict. It validates the bounded file first, registers the import, then processes batches.

Each batch transaction reloads the current checkpoint, upserts records and advances progress together. A failure before commit rolls back both. A failure after commit leaves a checkpoint that already describes persisted records. Restarting the same source resumes after that boundary.

```text
begin batch transaction
  read committed source checkpoint
  apply rows [checkpoint, next_checkpoint)
  update checkpoint / completion state
commit
(optional interruption after commit)
```

The fixture deliberately interrupts after the first two records commit. Restart begins from checkpoint 2 and completes at 3, with three records rather than duplicate inserts. Two concurrent importers reload checkpoint inside the serialized SQLite transaction and also finish with one import and three records.

```json
{
  "resume": {
    "committed_checkpoint_before_restart": 2,
    "final_checkpoint": 3,
    "final_records": 3
  },
  "concurrent_restart": {
    "callers": 2,
    "imports": 1,
    "records": 3
  }
}
```

### Identity and ordering are independent

The record key is (tenant_id, external_id), not filename or row number. A higher source_version updates it; a lower version cannot overwrite newer state. Equal version with different canonical content is rejected as an ambiguous source conflict. Source time is normalized provenance, not the sole conflict-resolution algorithm.

A timestamp-only last-write-wins rule can fail with clock skew, equal timestamps or old events arriving late. Use a source-provided monotonic revision when its scope/semantics are trustworthy, and define a tie policy. This fixture's integer version is a teaching contract, not a guarantee provided by arbitrary upstream files.

### Checkpoint design limits

The checkpoint is an ordinal in a fixed validated record sequence, not a byte offset into arbitrary CSV. Quoted multiline fields make physical line numbers a different concept. Reordering, replacing or reinterpreting bytes under the same import identity would invalidate the progress meaning; the digest guard blocks changed bytes here.

The example loads up to its row/byte limits into memory and validates before writes. Larger pipelines need staging, streaming or partitioning and a corresponding checkpoint/parser-version contract. Error reports should identify source/record/field/reason without echoing private raw values.

Do not advance progress before the data commit: restart could skip missing records. Do not maintain it in an unrelated transaction: interruption can produce a mismatch. Stable row identity makes replay safer, but it does not excuse silently losing source rows or overwriting a newer version.

## 15.10 Architectural understanding: build a tenant import service

Requirements: accept an authorized upload, retain immutable source identity, process outside the request, show progress/failure, avoid duplicate/stale records and keep read caches consistent with committed changes.

```text
client -> authorize tenant -> stage immutable source -> create import record/outbox
                                                      -> return job/status ID
dispatcher -> managed task or local queue
worker -> resolve trusted import/source
       -> parse + validate -> bounded record/checkpoint transactions
       -> durable completion/failure
       -> cache invalidation event -> catalog/dashboard readers
status API -> authorized import state and sanitized row diagnostics
```

The executed components are the local cache, SQLite job/effect protocol and restartable CSV importer with format adapters. The HTTP API, object storage, outbox dispatcher, managed queue and cross-process cache invalidation are architectural extensions.

### Build in useful increments

**Step 1: define source ownership and identity.** Authorize upload/status access, assign server-owned staging identity and tenant scope, and retain a digest. A filename or task payload URL is not authority. Bound accepted formats and upload size before parsing.

**Step 2: persist acceptance.** Store import metadata and queue intent with the transaction that promises the operation. Return a durable job/status ID only after acceptance commits. Add a dispatcher/reconciler for the database-to-queue gap.

**Step 3: define parse and validation policy.** Choose exact columns/encoding/sheets, amount/time types, duplicate-source rules and reject-all versus partial acceptance. The current CSV path uses reject-all preflight followed by restartable committed batches. Other adapters normalize records or produce reviewable evidence, but only CSV is wired to the durable importer here.

**Step 4: implement bounded worker transitions.** Resolve source bytes from trusted metadata, acquire ownership if the system requires it and process within configured budgets. Commit data and progress together. The importer serializes concurrent local progress transactions; a production distributed worker must choose the corresponding real database/queue protocol.

**Step 5: preserve operation and source versions.** Use stable tenant/source keys for rows, immutable import identity for progress and a declared upstream ordering rule. If the source changes, create a new version/import rather than silently resuming at an old ordinal.

**Step 6: connect committed writes to caches.** Invalidate after commit or publish an invalidation intent in the same transaction. Consider delayed/duplicate invalidations and stale in-flight fills. Stock/authorization decisions still consult the authoritative boundary.

**Step 7: make failure visible.** Distinguish invalid source, transient dependency failure, exhausted attempts, stale ownership and ambiguous provider outcomes. Store a terminal status and a replay policy. A worker returning success without recording its intended outcome loses observability and can lose work.

**Step 8: operate within capacity.** Bound concurrent jobs, active cache loads, parser processes, batch sizes and database leases. Monitor job age/queue delay, lease expiry, retry rates, rejected input, checkpoint lag, primary load and cache freshness. Raw queue depth alone cannot explain whether old work is stuck.

### Failure walkthrough

| Failure | Executed result / required extension |
| --- | --- |
| Cache entry expires | Local loader fetches again at the defined boundary |
| Eight same-key misses | One local load, seven observed followers |
| Writer invalidates during old load | Old response may finish; old result is not cached again |
| Two workers claim one local job | One active owner |
| Former owner reports after reclaim | Old token is rejected |
| Failure before local effect/done commit | Both local writes roll back |
| External effect completes but response is lost | Reconciliation/provider idempotency required; not executed |
| Formula/entity/over-budget fixture | Relevant parser policy rejects it |
| Import stops before batch commit | Data/checkpoint both roll back |
| Import stops after committed batch | Restart resumes at durable checkpoint |
| Older source arrives later | Lower version cannot replace newer record |
| Business commit succeeds but task creation fails | Outbox/reconciliation extension required |

### Common wrong answers

| Claim | Correction |
| --- | --- |
| “A ten-second TTL means every response is at most ten seconds behind a write.” | Loading/replica/race boundaries affect that claim; define the actual freshness contract. |
| “Deleting the cache after writing fixes every race.” | An older in-flight reader can fill after the delete unless the protocol prevents it. |
| “A queue guarantees exactly-once side effects.” | Delivery, local deduplication and external provider effects are separate boundaries. |
| “The lease expired, so the previous worker stopped.” | It may still run; reject stale ownership and fence the protected effect where required. |
| “Every error deserves another retry.” | Permanent defects, overload, deadline and ambiguous outcomes need different policies. |
| “Cloud Tasks is FIFO.” | Ordering is not guaranteed; use explicit source/state guards. |
| “A task-name duplicate check replaces application idempotency.” | Its scope/retention differs from a durable business operation record. |
| “Excel data_only evaluates formulas.” | It reads cached values; the example deliberately rejects formula cells. |
| “PDF extraction means the invoice is structured correctly.” | Text extraction, OCR, layout interpretation and domain validation are distinct. |
| “Checkpoint first, then save records.” | An interruption can make restart skip data that never committed. |

### Must remember

1. Authoritative state and reusable cached state have different failure policies.
2. Cache keys carry trusted scope and representation; authorization precedes protected cache reads.
3. TTL, capacity eviction, invalidation and work collapse solve different problems.
4. Process-local coordination cannot coordinate every application replica.
5. Stable business identity and payload checks make duplicate operations interpretable.
6. Lease expiry permits new ownership; it does not cancel old work.
7. Local effect/completion can share a transaction; external effects need their own replay/reconciliation protocol.
8. Managed task delivery still requires authenticated, duplicate-tolerant handlers.
9. Parse under a declared format/resource contract, then normalize and validate.
10. File identity, record identity and source ordering are different dimensions.
11. Commit progress with its data and keep resumed source interpretation stable.
12. Every result here is scoped to the actual local engine/library; service/production extensions remain explicit.

## 15.12 Interview questions and follow-ups

These are curated questions covering useful backend mechanisms, not measured company-frequency rankings. Practice a short explanation, then defend it with the relevant failure case.

**Q1. What is caching, and why use it?**

Caching reuses a result to reduce repeated work or dependency load. The cached value is usually disposable derived state with a freshness policy. Define what happens on miss/outage and which decisions must still consult authoritative data.

*Follow-up:* Would you use the cached stock display to authorize a purchase?

**Q2. Explain cache-aside.**

Read the cache, load authoritative data on a miss and store it for later reuse. After a committed primary write, invalidate or refresh affected representations. The separate primary/cache operations still have failure and ordering gaps.

*Follow-up:* Draw the old-reader/late-fill race.

**Q3. What is the difference between TTL and eviction?**

TTL applies an expiry policy to an entry. Eviction removes entries under a capacity policy, such as LRU. Either creates a miss, but they address freshness and bounded storage differently.

*Follow-up:* Can a key disappear before its TTL because of memory pressure?

**Q4. Does TTL guarantee strong consistency?**

No. The TTL boundary is tied to the cached fill, and delayed/stale loads can complicate any bound from a primary write. Running requests can also return older data. State the actual consistency contract rather than treating TTL as a transaction.

*Follow-up:* What does the local epoch specifically guarantee?

**Q5. What belongs in a cache key?**

Trusted resource/tenant identity and every context that changes the represented answer, such as schema version, filters or permission projection. Authorization must still happen. Use a stable unambiguous encoding and avoid exposing credentials/private values in keys/logs.

*Follow-up:* Why is tenant scope alone insufficient for user-filtered results?

**Q6. What is negative caching?**

Temporarily retaining an authoritative absent result so repeated missing lookups avoid primary work. Use an appropriate short TTL and trusted scope. Do not cache a transient database failure as “does not exist.”

*Follow-up:* What happens if the object is created during the negative TTL?

**Q7. What is a cache stampede?**

Many callers load the same missed/expired key simultaneously, multiplying primary work. Single-flight coordination collapses local work; jittered expiry or distributed coordination can address wider bursts. Each needs a bounded failure/deadline policy.

*Follow-up:* What did the eight-thread fixture actually prove?

**Q8. How can invalidation still return stale data?**

A reader can load old data before the writer commits, then fill after the writer invalidates. The local epoch prevents that old fill from being stored, but does not cancel its existing response or coordinate another process's cache.

*Follow-up:* Which component would enforce a distributed version/fencing rule?

**Q9. What happens when Redis is unavailable?**

Follow a bounded product policy: fallback to authoritative data only within its capacity, serve permitted stale data or return controlled failure. Unlimited simultaneous fallback can overload the database. Monitor dependency/loader waits and freshness as well as hits.

*Follow-up:* Does making the cache optional make its outage harmless?

**Q10. Is a Redis lock just SET NX plus DEL?**

Ownership and expiry matter. Release must atomically verify the current token; an expired old owner must not delete a successor's lock. Correctness-critical protected work may need fencing beyond a cache lock.

*Follow-up:* Why doesn't lease expiry prove the former worker stopped?

**Q11. How do a queue, cron and an in-process task differ?**

A queue retains/delivers work, cron triggers schedules, and an in-process task runs within one application's lifetime. A scheduled or background operation still needs durable acceptance, overlap rules and retries when its loss is unacceptable.

*Follow-up:* What should an API returning 202 persist first?

**Q12. What makes a worker idempotent?**

A repeated business operation has a safe stable result/effect, enforced with durable identity, payload/state checks and atomic transitions. Merely checking a process-local flag or receiving one task name does not cover crashes, new deliveries or multiple replicas.

*Follow-up:* How does the unique tenant/operation key participate?

**Q13. How do two workers avoid claiming the same local job?**

The fixture selects and updates ownership inside one BEGIN IMMEDIATE transaction. Separate SQLite connections serialize that claim. Other engines/brokers need their own verified protocol; this is not evidence about PostgreSQL row locking.

*Follow-up:* What did M13's SKIP LOCKED example demonstrate instead?

**Q14. What is a lease token for?**

To identify the current owner when completing, failing or renewing a job. Reclaim rotates it, so a former owner cannot mutate the new owner's local state. It does not automatically fence an external API.

*Follow-up:* Which predicate rejects the stale completion?

**Q15. What is the difference between duplicate delivery and exactly-once effect?**

Delivery can repeat. A local database effect can be deduplicated and committed with completion, while external effects have another acknowledgment/crash boundary. Use provider idempotency and reconciliation where available; avoid universal exactly-once claims.

*Follow-up:* Describe the send-before-mark failure window.

**Q16. How do you choose retry policy?**

Classify transient versus permanent/ambiguous failure, set attempt/age/deadline budgets, use bounded backoff/jitter where appropriate and account for overload/provider guidance. Nested retry layers need one total budget. Immediate retries can amplify failure.

*Follow-up:* Which part of the local 2,4,8,8 sequence is deliberately omitted?

**Q17. What should happen to permanently failed work?**

Persist a terminal business outcome with sanitized diagnosis, retention and an explicit replay/repair policy. Do not silently loop or discard the only evidence. A failed-job store and an external broker's retry behavior are not automatically the same feature.

*Follow-up:* Why can replaying old failed imports overwrite newer state without a version rule?

**Q18. How does Cloud Tasks work?**

A producer creates an HTTP-target task in a managed queue; the service dispatches it to a handler according to schedule/rate/retry configuration. The handler authenticates the dispatch and owns durable business completion and duplicate safety.

*Follow-up:* Which parts were actually executed in this module?

**Q19. Does Cloud Tasks guarantee ordering or no duplicates?**

No FIFO guarantee is provided, and duplicate executions can occur. Task-name deduplication covers creation under service rules, not all business effects forever. Workers need durable identity and ordering/state guards where the domain requires them.

*Follow-up:* How would a versioned import handle an older task arriving later?

**Q20. How should a Cloud Tasks handler authenticate a request?**

Use the selected authenticated service identity/token configuration and validate the expected token claims through the platform/verifier. Informational task headers are not proof of origin. Then resolve trusted business/tenant state rather than accepting arbitrary source paths.

*Follow-up:* Does a valid dispatcher identity authorize every payload tenant?

**Q21. Why are rate and concurrency separate?**

Rate controls dispatch over time; concurrency controls simultaneous in-flight work. Slow handlers can occupy every slot at a low rate, while bursts can pressure dependencies. Raising concurrency cannot create capacity in an overloaded database/provider.

*Follow-up:* Which metrics distinguish queue delay from handler execution time?

**Q22. What is the producer dual-write problem?**

Business state and remote enqueue are separate commits. A stop between them can leave missing work or a task for rolled-back state. Store queue intent with business state in a transactional outbox, then dispatch/reconcile with stable identity.

*Follow-up:* Does atomic outbox insertion prove the remote task was delivered?

**Q23. Why not parse CSV using split(',')?**

CSV quoting and embedded delimiters/newlines require a real parser. Then apply explicit encoding/header/type/resource policies. Parsing returns fields; it does not validate currency, tenant ownership, source identity or timestamps.

*Follow-up:* How is a checkpoint ordinal different from a physical line number?

**Q24. What are important Excel ingestion traps?**

ZIP expansion, unexpected sheets/dimensions, mixed cell types, formulas/cached results and macro content. Use declared schema and bounds, close read-only workbooks and define formula policy. The fixture rejects formulas instead of evaluating or trusting them.

*Follow-up:* What does data_only actually select?

**Q25. Why use a hardened XML parser?**

Untrusted XML can contain dangerous DTD/entity/external constructs. Explicit parser policy reduces those risks, while byte/nesting/time/memory limits still matter. The fixture verifies defusedxml rejection but is not a general resource sandbox.

*Follow-up:* Why can a small source expand into more parsing work?

**Q26. Does PDF text extraction produce reliable records?**

No. Text extraction, reading order, layout/table interpretation, OCR and business validation are separate steps. The fixture extracts text and rejects empty/encrypted/over-page inputs; it does not infer invoice amounts or run OCR.

*Follow-up:* Where would review/confidence policy belong?

**Q27. How do you make an import restartable?**

Bind progress to immutable source identity and stable interpretation, use scoped row identities and commit each batch's rows/checkpoint together. Restart reads the committed checkpoint, not a process-local counter. Replayed rows still need safe upsert/version semantics.

*Follow-up:* What happens if the checkpoint commits before the rows?

**Q28. How do you handle out-of-order source updates?**

Use a declared source version/ordering contract and conditional writes. Lower versions cannot overwrite higher versions; equal-version changed content needs a conflict policy. A timestamp or local arrival order alone can be misleading.

*Follow-up:* What does the fixture do with equal version and different content?

**Q29. Reject the whole file or accept valid rows?**

Choose explicitly from the product requirement. This bounded example validates the whole input before mutation, then supports partial committed batches only for execution interruptions. A partial-row policy needs durable rejected-row diagnostics, counts and replay semantics.

*Follow-up:* Can “partial import” mean both validation and execution failures?

**Q30. How would you combine caches, jobs and ingestion in a real system?**

Persist authorized upload/import identity and queue intent, process immutable source with safe retries/checkpoints, store visible outcomes and propagate cache invalidation after committed changes. Bound resource use and reconcile external gaps. Explain the actual verified boundary for every component.

*Follow-up:* Name one failure window and the durable state that recovers it.
