# Module 6: Memory Management

**Module 6 · 4 hours · Tier 1 · Requires: M1 (process memory layout), M0 (kernel mode)**

---

## Why this module matters

Memory-management questions come in two flavours. **Conceptual:** logical vs physical address, internal vs external fragmentation, paging vs segmentation, what a TLB is. **Numerical:** split an address into page number and offset, compute page-table size, compute effective access time with a TLB. Both depend on one mental picture, **address translation**, and this module builds it step by step: base/limit registers → paging → TLB → multi-level tables. M7 (virtual memory) then extends the same picture to "the page isn't in RAM".

**Every numerical in this module was computed with code.**

The organising principle:

> **Programs use logical addresses; RAM uses physical addresses. The MMU translates every single memory access between them, in hardware, using tables the kernel maintains. Paging chops both spaces into equal-size pieces so that any page can go in any frame, which eliminates external fragmentation, and the TLB caches recent translations so that this costs almost nothing.**

---

## 6.1 Goals of memory management

| Goal | Meaning |
|---|---|
| **Protection** | A process can't read or write another process's (or the kernel's) memory |
| **Relocation** | A program can be loaded anywhere in RAM (and moved) without being rewritten |
| **Sharing** | Processes can share memory deliberately (shared libraries, shared memory IPC) |
| **Efficient use** | Minimal waste (fragmentation), many processes resident |
| **Abstraction** | Each process sees a simple, private, contiguous address space |

---

## 6.2 Logical vs physical addresses and the MMU

### 1. Definitions

| | Logical (virtual) address | Physical address |
|---|---|---|
| Generated by | The **CPU**, i.e. the program | The **MMU**, after translation |
| Seen by | The process | The memory hardware |
| Range | 0 … the process's address-space size | 0 … installed RAM |
| Same value for every process? | Yes: every process can use address 0x400000 | No: each maps to different RAM |

The set of all logical addresses is the **logical address space**; the set of physical addresses is the **physical address space**.

### 2. Address binding: when do addresses become physical?

| Binding time | How | Consequence |
|---|---|---|
| **Compile time** | The compiler emits absolute physical addresses | The program must load at that exact location (old MS-DOS `.COM` programs) |
| **Load time** | The loader adjusts addresses when loading (relocatable code) | It can't move after loading |
| **Execution time** | Translation on **every access** by the MMU | It can move at any time. **This is what modern OSes do** |

### 3. The simplest MMU: base (relocation) and limit registers

```
                       limit register             relocation (base) register
                            |                               |
  CPU --logical addr--> [ addr < limit ? ] --yes--> [ + base ] --physical addr--> RAM
                            |
                            no -> TRAP: addressing error (segmentation fault)
```

- **Limit** gives protection: a process can't reach beyond its region.
- **Base** gives relocation: the same logical address 0 maps to wherever the process was loaded.
- Only the **kernel** can load these registers (privileged instructions, M0).

**Its limitation:** each process needs **one contiguous** chunk of physical memory, which leads directly to external fragmentation (§6.3). Paging removes the contiguity requirement.

## 6.3 Contiguous allocation and fragmentation

### 1. Fixed vs variable partitions

| | Fixed (static) partitions | Variable (dynamic) partitions |
|---|---|---|
| How | RAM pre-divided into fixed-size partitions; one process per partition | Each process gets exactly what it needs from a **hole** (free block) |
| Waste | **Internal** fragmentation (a partition is larger than the process) | **External** fragmentation (free memory scattered in small holes) |
| Degree of multiprogramming | Limited by the number of partitions | Flexible |

### 2. Placement strategies for variable partitions

| Strategy | Rule | Characteristics |
|---|---|---|
| **First fit** | The **first** hole that's big enough | Fast; generally good in practice |
| **Best fit** | The **smallest** hole that's big enough | Leaves tiny, useless slivers; must search the whole list (or keep it sorted) |
| **Worst fit** | The **largest** hole | Leaves big leftovers, but simulations show it's generally the worst |
| **Next fit** | Like first fit, but resume from where the last search stopped | Spreads allocations around |

Simulations show first fit and best fit beat worst fit on storage use, and first fit is usually faster.

### 3. Worked example (verified)

Free holes (in order): **100, 500, 200, 300, 600 KB**. Requests in order: **212, 417, 112, 426 KB**. Leftover space in a hole stays usable.

| Strategy | 212 | 417 | 112 | 426 | Result |
|---|---|---|---|---|---|
| **First fit** | 500 (→288 left) | 600 (→183) | 288 (→176) | **must wait** (largest hole 300) | 3 of 4 placed |
| **Best fit** | 300 (→88) | 500 (→83) | 200 (→88) | 600 (→174) | **All 4 placed** |
| **Worst fit** | 600 (→388) | 500 (→83) | 388 (→276) | **must wait** (largest hole 300) | 3 of 4 placed |

Here best fit wins, because it saves the large 600 KB hole for the large request. (On other workloads first fit wins. That's why it's "generally" good, not always.)

### 4. Internal vs external fragmentation (the comparison)

| | Internal fragmentation | External fragmentation |
|---|---|---|
| Definition | Wasted space **inside** an allocated block (allocated > requested) | **Total free memory is enough**, but it's split into **non-contiguous** holes, none big enough |
| Where it occurs | Fixed partitions, **paging** (the last page of a process), allocators rounding sizes up | Variable partitions, **segmentation** |
| Example | A process needs 18 KB; it gets five 4 KB pages (20 KB), wasting 2 KB | 3 free holes of 100 KB each, and a 250 KB request fails |
| Fixes | Smaller allocation units (at the cost of more overhead) | **Compaction**, or **paging** (non-contiguous allocation) |

**Compaction:** move processes to merge the holes into one block. It requires execution-time binding (relocation), and it's **expensive**: copying memory, with processes paused.

**50-percent rule (first fit, statistical):** for N allocated blocks, about **0.5N** blocks are lost to fragmentation, so **one-third** of memory may be unusable.

## 6.4 Paging

### 1. The idea

- Divide **physical memory** into fixed-size blocks called **frames**.
- Divide each **logical address space** into blocks of the **same size** called **pages**.
- Any page can be placed in **any free frame**; a per-process **page table** records where each page lives.

```
 Logical memory (process)        Page table            Physical memory (frames)
 +--------+                     +------+-------+      frame 0 [         ]
 | page 0 | ------------------> |  0   |   5   |      frame 1 [ page 3  ]
 | page 1 | ------------------> |  1   |   2   |      frame 2 [ page 1  ]
 | page 2 | ------------------> |  2   |   7   |      frame 3 [ other   ]
 | page 3 | ------------------> |  3   |   1   |      frame 4 [ other   ]
 +--------+                     +------+-------+      frame 5 [ page 0  ]
   contiguous to the process                          frame 6 [         ]
                                                      frame 7 [ page 2  ]
                                                    NOT contiguous in RAM: no external fragmentation
```

### 2. Address translation

A logical address splits into a **page number (p)** and a **page offset (d)**:

```
 logical address (m bits)   =  [ page number p  (m - n bits) | offset d (n bits) ]     page size = 2^n

 physical address           =  [ frame number f              | offset d          ]
                                       ^
                                 f = page_table[p]
```

The offset is **copied unchanged**; only the page number is translated. Page sizes are powers of 2, so the split is just taking bits, with no division needed in hardware.

### 3. Translation numericals (verified)

**Example 1.** Page size 4 KB (4096 bytes), logical address **20000**.
- Page number = ⌊20000 / 4096⌋ = **4**; offset = 20000 mod 4096 = **3616**.

**Example 2.** Page size 4 KB; page table: page 0→frame 5, 1→2, 2→7, **3→1**, 4→9. Translate logical address **13500**.
- Page = ⌊13500 / 4096⌋ = **3**, offset = 13500 − 3·4096 = **1212**.
- Frame = page_table[3] = **1**.
- Physical = 1 × 4096 + 1212 = **5308**.

**Example 3: address split and page-table size.** 32-bit logical addresses, 4 KB pages, 4-byte page-table entries (PTEs).
- Offset bits = log₂(4096) = **12**; page-number bits = 32 − 12 = **20**.
- Entries = 2²⁰ = **1,048,576** (about a million).
- Page-table size = 2²⁰ × 4 B = **4 MB per process**, too big to allocate contiguously for every process. This motivates multi-level page tables (§6.6).

**The formulas:**
```
 offset bits         = log2(page size)
 page-number bits    = logical address bits - offset bits
 # pages / entries   = 2^(page-number bits) = logical address space / page size
 # frames            = physical memory / frame size
 page-table size     = # entries x PTE size
 frame-number bits   = log2(# frames)
```

### 4. What's in a page-table entry (PTE)

| Bit / field | Purpose |
|---|---|
| **Frame number** | Where the page is in RAM |
| **Valid / present bit** | Is this page in RAM (and part of the address space)? If not → page fault (M7) |
| **Protection bits** | Read / write / execute permissions; writing to read-only memory traps (that's how COW works, M1/M7) |
| **Dirty (modified) bit** | Has the page been written since it was loaded? (M7: dirty pages must be written back before eviction) |
| **Referenced (accessed) bit** | Was it used recently? (M7: approximating LRU) |
| User/supervisor bit | Kernel-only pages |

### 5. Properties of paging

| Property | Explanation |
|---|---|
| **No external fragmentation** | Any free frame can hold any page |
| **Internal fragmentation** only in the **last page** | On average **half a page** per process |
| **Sharing** | Several page tables can point to the **same frame**: shared code (libc), shared memory. Code must be read-only (reentrant) |
| **Protection** | Per-page permission bits plus a valid bit; each process sees only its own mappings |
| **Cost** | Every access needs a page-table lookup (an extra memory access → the TLB fixes this) |

### 6. Page-size trade-off

| Smaller pages | Larger pages |
|---|---|
| Less internal fragmentation | More internal fragmentation |
| **Bigger page tables** | Smaller page tables |
| Less TLB reach (more misses) | **More TLB reach** |
| Finer-grained I/O | Fewer, larger transfers |

Typical size: **4 KB**, with **huge pages** (2 MB / 1 GB on x86-64) for databases and VMs that want a larger TLB reach.

## 6.5 The TLB (Translation Lookaside Buffer)

### 1. The problem

With the page table in RAM, **every memory access becomes two**: one to read the PTE and one for the data. That halves performance.

### 2. The solution

The **TLB** is a small, very fast **cache of recent page→frame translations**, inside the MMU. It's associative: all entries are searched in parallel. Typical size: tens to a few thousand entries.

```
 logical addr [ p | d ]
       |
       +--> TLB lookup (p) --HIT--> frame f -------------------+
       |         |                                              |
       |        MISS                                            v
       |         +--> page table in RAM: f = PT[p]  ----> [ f | d ] --> RAM access
       |               (then insert p->f into the TLB, evicting an old entry)
```

### 3. Effective access time (EAT): the standard numerical

```
 h = TLB hit ratio, t = TLB lookup time, m = memory access time   (single-level page table)

 EAT = h * (t + m)  +  (1 - h) * (t + m + m)
       hit: TLB + data    miss: TLB + page-table read + data

 With a k-level page table, a miss costs t + k*m + m:
 EAT = h*(t + m) + (1 - h)*(t + (k + 1)*m)
```

**Worked (verified): t = 20 ns, m = 100 ns.**

| Hit ratio | EAT | vs. no paging (100 ns) | vs. paging without a TLB (200 ns) |
|---|---|---|---|
| **80%** | 0.8 × 120 + 0.2 × 220 = **140 ns** | 40% slower | 30% faster |
| **98%** | 0.98 × 120 + 0.02 × 220 = **122 ns** | 22% slower | 39% faster |
| 98%, **2-level** page table | 0.98 × 120 + 0.02 × 320 = **124 ns** | | |

**Conventions differ:** some problems assume the TLB lookup overlaps the memory access, or that the TLB time is negligible (t = 0). Then EAT = h·m + (1−h)·2m. **Say which convention you're using.** The structure of the formula is what's being tested.

### 4. Why hit ratios are so high: locality

Programs exhibit **locality of reference**:
- **Temporal:** recently used data is likely to be used again soon (loop variables).
- **Spatial:** nearby addresses are likely to be used (array traversal, sequential code).

One 4 KB page covers 1024 consecutive `int`s, so a loop over an array misses the TLB once per page. Real hit ratios are typically **above 99%**.

### 5. TLB and context switches

The TLB holds translations for **one** address space. On a process switch, either:
- **flush the TLB** (simple; the new process starts with all misses: an indirect cost of context switching, M1 §1.5), or
- tag entries with an **ASID** (address-space ID; on x86, **PCID**), so entries from several processes coexist and no flush is needed.

**TLB reach** = number of entries × page size: how much memory can be accessed without TLB misses. Huge pages increase it dramatically.

## 6.6 Structuring large page tables

A flat page table for a 64-bit address space would be astronomically large. Three solutions:

### 1. Hierarchical (multi-level) paging

Page the page table itself. A 32-bit, 4 KB example (two-level):

```
 logical address:  [ p1 (10 bits) | p2 (10 bits) | offset (12 bits) ]

  outer page table --p1--> inner page table --p2--> frame --+offset--> physical
  (1 page)                 (only the inner tables that are ACTUALLY USED are allocated)
```

**Why it saves memory:** a process using only a few MB of its 4 GB address space needs the outer table plus a handful of inner tables, not all 1024 inner tables. **Unused regions cost nothing.**

**x86-64 uses 4 levels** (48-bit virtual addresses: 9 + 9 + 9 + 9 index bits + 12 offset bits), and newer CPUs support **5 levels** (57-bit). Cost: a TLB miss requires walking 4 levels, i.e. 4 memory reads. That's why the TLB hit ratio matters so much, and why CPUs cache page-walk entries too.

### 2. Hashed page tables

Hash the virtual page number into a table of chains holding (page, frame) pairs. Common for address spaces larger than 32 bits in older designs; handles sparse address spaces well.

### 3. Inverted page table

**One table for the whole system**, with **one entry per physical frame** (holding which process and page occupy it), instead of one table per process with one entry per virtual page.

| | Regular (per-process) page table | Inverted page table |
|---|---|---|
| Number of tables | One per process | **One** system-wide |
| Entries | One per **virtual page** | One per **physical frame** |
| Size scales with | Virtual address space × processes | **Physical memory** |
| Lookup | Direct index (fast) | **Search** for (pid, page): needs a hash table to be practical |
| Sharing memory | Easy (two PTEs → one frame) | Hard (one entry per frame holds one mapping) |
| Used in | x86, ARM (multi-level) | PowerPC, IA-64 (historically) |

## 6.7 Segmentation

### 1. The idea

Divide a program into **variable-size logical units** that match the programmer's view: code, data, heap, stack, each library, each module. A logical address is a pair **⟨segment number, offset⟩**.

```
 logical address <s, d>
        |
        v
  segment table [s] = (base, limit)
        |
        +--> d < limit ?  -- no --> TRAP (segmentation fault)
        |       yes
        v
  physical = base + d
```

**Example:** segment table: seg 0 (base 1400, limit 1000), seg 1 (base 6300, limit 400), seg 2 (base 4300, limit 400).
- ⟨2, 53⟩ → 53 < 400 ✓ → **4353**.
- ⟨1, 500⟩ → 500 ≥ 400 → **trap** (addressing error).

### 2. Properties

| Pros | Cons |
|---|---|
| Matches the logical structure of programs | **External fragmentation** (variable-size segments: back to the hole problem) |
| Natural per-segment protection (code read+execute, data read+write) | Compaction may be needed |
| Easy sharing of whole segments (a library segment) | Segments can be large, so contiguous placement is hard |

**The term "segmentation fault"** comes from this model: accessing outside a segment's limit. Today Linux raises SIGSEGV for any invalid access, including unmapped pages.

### 3. Segmentation with paging

Each segment is itself paged: the logical structure of segmentation plus the fragmentation-free placement of paging. Historically used by x86-32 (segment registers + paging). **x86-64 essentially disables segmentation** (a flat model, with only the FS/GS registers still used, for thread-local storage).

---

## 6.8 Paging vs segmentation (the comparison)

| | Paging | Segmentation |
|---|---|---|
| Unit | **Fixed-size** pages | **Variable-size** segments |
| Division decided by | Hardware/OS (invisible to the programmer) | The program's **logical structure** (visible) |
| Address | Single linear address, split by hardware into page + offset | Two-part ⟨segment, offset⟩ |
| Table | Page table: page → frame | Segment table: segment → (base, limit) |
| Fragmentation | **Internal** (last page) | **External** |
| Protection / sharing granularity | Per page | Per logical unit (more natural) |
| Size check | Implicit (offset < page size by construction) | Explicit (offset < limit) |
| Modern use | **Universal** (all modern OSes) | Largely obsolete as a standalone; x86-64 is flat |

**Model answer:** *"Paging splits memory into fixed-size pages and frames, so any page fits any frame: no external fragmentation, but a little internal fragmentation in the last page, and the division is invisible to the programmer. Segmentation splits memory into variable-size logical units like code, data and stack, which gives natural protection and sharing but causes external fragmentation. Modern systems use paging; x86 once combined both, by paging each segment."*

## 6.9 Swapping (briefly)

Moving an **entire process** (or, in modern systems, individual pages) between RAM and a **backing store** (the swap area on disk) to free memory.

- **Classic swapping** (whole processes) is mostly obsolete: transferring hundreds of MB is too slow.
- **Modern systems page instead** (M7): only individual pages move between RAM and swap.
- The **medium-term scheduler** (M1) decides which processes to swap out under memory pressure.
- Mobile OSes (iOS, Android) generally **don't swap to flash** (wear, latency). They **kill background apps** instead (Android's low-memory killer), or compress memory.

## 6.10 Consolidation

### Must remember (module)

1. Logical (CPU-generated) vs physical (seen by RAM); the MMU translates on every access (execution-time binding).
2. Base + limit registers = relocation + protection, but they require contiguous allocation.
3. First/best/worst fit; worst is generally worst. Internal (inside a block) vs external (scattered holes) fragmentation; compaction is expensive.
4. Paging: pages ↔ frames of the same size; logical address = page | offset; physical = frame | offset; the offset is unchanged.
5. **Offset bits = log₂(page size); entries = 2^(page bits); table size = entries × PTE size.** 32-bit with 4 KB pages → 2²⁰ entries → 4 MB at 4 B/PTE.
6. Paging: no external fragmentation; on average half a page of internal fragmentation per process; easy sharing.
7. PTE bits: frame, valid, protection, dirty, referenced.
8. TLB = cache of translations; **EAT = h(t+m) + (1−h)(t+2m)**; 20/100 ns: 80% → 140 ns, 98% → 122 ns. State your conventions.
9. Locality makes the TLB effective; ASIDs/PCIDs avoid flushes on context switches.
10. Multi-level page tables avoid allocating tables for unused regions; x86-64 uses 4 (or 5) levels. Inverted = one entry per frame (small, but a search).
11. Segmentation: variable logical units, ⟨s, d⟩, base + limit check, external fragmentation.
12. Paging vs segmentation: fixed/invisible/internal fragmentation vs variable/logical/external fragmentation.

### Common wrong answers (module)

- "Paging has no fragmentation at all." (It has internal fragmentation.)
- "Segmentation has internal fragmentation."
- "The TLB stores data." (It caches **translations**; data caching is the L1/L2/L3 caches.)
- "The page table is stored in the TLB." (The page table lives in RAM; the TLB caches a few entries.)
- "Logical and physical address spaces must be the same size."
- "Bigger pages are always better."
- Forgetting that a TLB miss with a k-level table costs k extra memory accesses.

### Practice numericals

**N1.** Logical address space 64 KB, page size 1 KB, physical memory 32 KB. How many bits are in a logical address, a physical address, and an offset? How many pages and how many frames?
<details><summary>Answer</summary>

Logical: 64 KB = 2¹⁶ → **16 bits**. Physical: 32 KB = 2¹⁵ → **15 bits**. Offset: 1 KB = 2¹⁰ → **10 bits**. Pages: 2¹⁶/2¹⁰ = **64** (6-bit page number). Frames: 2¹⁵/2¹⁰ = **32** (5-bit frame number).
</details>

**N2.** Page size 2 KB; page table: 0→3, 1→6, 2→0, 3→9. Translate logical addresses 3000 and 7000.
<details><summary>Answer</summary>

3000: page ⌊3000/2048⌋ = 1, offset 952 → frame 6 → 6·2048 + 952 = **13240**. 7000: page 3, offset 7000 − 6144 = 856 → frame 9 → 18432 + 856 = **19288**.
</details>

**N3.** TLB lookup 10 ns, memory access 100 ns, single-level paging. What hit ratio gives an EAT of 120 ns?
<details><summary>Answer</summary>

EAT = h(110) + (1−h)(210) = 210 − 100h = 120 → **h = 0.9 (90%)**.
</details>

**N4.** 48-bit virtual addresses, 4 KB pages, 8-byte PTEs. How big would a single-level page table be? Why does x86-64 use 4 levels with 9 bits each?
<details><summary>Answer</summary>

Page bits = 48 − 12 = 36 → 2³⁶ entries × 8 B = **2³⁹ B = 512 GB** per process, which is impossible. With 4 KB pages and 8 B entries, **one page holds 512 = 2⁹ entries**, so each level indexes with 9 bits and every table fits exactly in one page: 4 × 9 + 12 = 48.
</details>

**N5.** A process needs 72,766 bytes and the page size is 2048 bytes. How many pages does it get, and how much internal fragmentation is there?
<details><summary>Answer</summary>

72,766 / 2048 = 35.53 → **36 pages** (73,728 bytes). Internal fragmentation = 73,728 − 72,766 = **962 bytes**.
</details>
